# Build journal

What was built per step and why, for the owner to read; quiz questions per phase at the end of each phase section.

## Phase 0 — Bootstrap

### 0.1 — git init, ignore, node version
The repository was initialised on `main` with a pinned Node major (`.nvmrc` = 22) and an `.editorconfig` so every editor produces the same whitespace. The existing `.gitignore`, `CLAUDE.md` and `docs/plan/` were picked up as they were. Why `.env.*` is ignored but `.env.example` is force-included: real env files hold secrets and must never be committed, so a wildcard blocks every variant; the `!.env.example` exception lets the one file that documents variable names (without values) stay tracked so a fresh clone knows what to set.

### 0.2 — pnpm workspace + root package.json
The root `package.json` is private and only holds scripts, the pinned `packageManager` (pnpm 12.16.1) and TypeScript; `pnpm-workspace.yaml` says every folder under `apps/` and `packages/` is a workspace. `tsconfig.base.json` holds the strict compiler settings that each workspace extends, and the root `tsconfig.json` is a "solution" file that `tsc -b` follows through project references (it stays empty until step 0.3 adds the first workspace, so `pnpm typecheck` only becomes meaningful then). pnpm's `node_modules` is strict: a package can only import what it declares in its own `package.json`, so there are no phantom dependencies that work by accident on your machine and break in CI. The `workspace:*` protocol makes one workspace depend on another by linking the local folder instead of fetching from the registry.

### 0.3 — packages/shared skeleton
`@store/shared` holds what the API and web must agree on: money helpers, the API error-code enum with its HTTP statuses, and an empty `schemas/` folder for Zod. It ships TypeScript sources through `exports` (no build step), so the consumers' own tooling compiles it. The first test file pins down rounding, the negative/float guards and currency formatting. Integer cents because floats cannot represent 0.1 exactly, so sums drift and no longer match Stripe to the cent; `Intl.NumberFormat` over hand-formatting because it knows each currency's decimals, symbol position and locale grouping, which string concatenation gets wrong.

### 0.4 — apps/api skeleton
The API is an Express 5 app with one route, `GET /api/v1/health`, request logging through pino-http and a Zod-validated `env.ts` (the only place dotenv is imported). `createApp()` builds and returns the app and `index.ts` only reads config and calls `listen`; a Supertest test drives the app without a port. Why split: tests can create fresh isolated apps in milliseconds, and importing the app never has side effects such as binding a port. ESM in Node 22: the package is `"type": "module"`, so imports are real ES modules and relative imports must carry their file extension at runtime, which is why the source writes `./app.ts` and the build step rewrites it to `./app.js`.

### 0.5 — apps/web skeleton
The web app is a hand-assembled Vite + React 18 + TypeScript project using the SWC plugin, with Tailwind 3 (config + PostCSS), React Router and TanStack Query installed, and one page that shows `api: ok` from the health endpoint via a typed function in `src/api/health.ts` (no fetching inside components, per the guard-rails). One component test proves jsdom, Testing Library and jest-dom work together. The Vite dev proxy forwards `/api` to :3000, so the browser only talks to its own origin: cookies are same-origin and there is no CORS to configure locally. SWC (Rust) compiles TSX and applies React Fast Refresh much faster than Babel for the same result. React StrictMode intentionally mounts, unmounts and remounts components in development to flush out effects that are not cleanup-safe, so double logs in dev are expected and absent in production.

### 0.6 — lint + format
One root flat `eslint.config.js` lints every workspace with typescript-eslint's type-checked recommended rules, `react-hooks` for the web app, `import/order`, a ban on default exports (except tool configs and route pages) and a ban on `any` and `@ts-ignore`. Prettier is set to 100 columns, single quotes, trailing commas; `simple-git-hooks` installs a pre-commit hook (via `pnpm prepare`) that runs `lint-staged`. A deliberately bad file was staged to prove the hook blocks the commit with nine errors, then removed. Flat config is a plain JS array of config objects (explicit, composable, one file) replacing the legacy cascading `.eslintrc` with its implicit `extends` and per-folder files. Hooks only touch staged files because linting the whole repo on every commit is slow enough that people start bypassing the hook; CI still checks everything.

### 0.7 — docker compose for local services
`docker-compose.yml` runs Postgres 16 (database `ecommerce`, data in a named volume, healthcheck via `pg_isready`) and Mailpit (SMTP on 1025, web UI on 8025), both bound to 127.0.0.1 only. A one-line init script creates a second database, `ecommerce_test`, the first time the volume is created. `.env.example` documents every variable so far (`NODE_ENV`, `PORT`, `DATABASE_URL`, `DATABASE_URL_TEST`, `WEB_ORIGIN`, `LOG_LEVEL`). Why a separate test DB: integration tests truncate or roll back freely, which must never be able to wipe the data you are developing against. A healthcheck says whether a service is actually ready to accept work, while `depends_on` alone only orders container start; combining them (`condition: service_healthy`) is what makes "start the API after Postgres is ready" reliable.

### 0.8 — CI skeleton
`.github/workflows/ci.yml` runs on every push and pull request with two parallel jobs: `check` (typecheck, lint, format check) and `test` (Postgres service container, then `pnpm test`; a comment marks where `db:migrate` joins in phase 1). It could not be run here (no `act`, no remote), so it was validated by Prettier parsing it and by repeating the same commands in a clean clone. A service container is a Docker container GitHub starts beside the job and health-checks before your steps run, so tests talk to a real Postgres on `localhost:5432` just like locally. Caching the pnpm store (keyed on the lockfile) makes installs mostly local copies instead of downloads. `concurrency` with `cancel-in-progress` cancels the older run of the same branch when a new push arrives, saving free-tier minutes.

### 0.9 — README stub
The README is a deliberately small stub: a working title, one line on what the project is, a work-in-progress note and the commands to run it locally and to run the checks. GitHub repo creation and the first push were intentionally skipped; they wait for the owner's go and his choice of repository name. The stub is honest about what does not exist yet (migrations and seed arrive in phase 1) so a fresh clone is never misleading.

## Phase 1 — Database

### 1.1 — Drizzle setup
The API now has a Drizzle client (`postgres` pool with `max` 10 and an idle timeout), a Zod-validated `DATABASE_URL`, a `drizzle.config.ts` and a migrator script behind `pnpm db:migrate`. Migration 0000 is hand-written SQL: the `citext` extension and the `set_updated_at()` trigger function that every table will attach. Migrations are the source of truth because they are the exact, reviewed, replayable history that production runs; `drizzle-kit generate` writes that history as SQL files, while `push` diffs the schema against a live database and mutates it with no record, so it is for throwaway experiments only. The env is validated at boot so a missing or malformed variable stops the process with a clear message, instead of surfacing as a confusing failure on the first query.

### 1.2 — users, sessions, addresses
Three tables per the data model, with the shared id/timestamp columns in one helper file and `updated_at` bumped by a trigger attached in the migration. I read the generated SQL (it matched the schema, and I appended the two trigger lines by hand). A smoke test inserts a user, proves case-insensitive email uniqueness, cascades a delete to sessions and addresses, and proves the partial unique index. `citext` is text compared case-insensitively, so one email cannot register twice as `A@x.com` and `a@x.com` without remembering to lowercase everywhere. A partial unique index only covers rows matching its `WHERE`, which is how "at most one default address per user" is enforced while non-default rows stay unlimited. `ON DELETE CASCADE` means deleting a user silently deletes their sessions and addresses in the same statement: great for cleanup, dangerous if a table that must outlive the user (orders, later) were wired to cascade, which is why orders use a nullable, non-cascading `user_id`.

### 1.3 — catalog tables
Categories (self-referencing parent), products, variants, images and inventory are in migration 0002, with GIN indexes on `search_vector` and `attributes` and a trigger per table. `search_vector` is a stored generated column: Postgres recomputes `to_tsvector('english', name || ' ' || description)` on every write, so it can never go stale and the app never writes it; the test searches it with `to_tsquery` and shows stemming ("napping" matches "naps"). A B-tree orders and compares whole values (equality, ranges, sorting), while a GIN index maps each lexeme or JSON key to the rows containing it, which is what "contains this word/key" queries need. `options jsonb` is unique per product because one combination such as red + small must be exactly one sellable thing; without it the cart could hold two "identical" variants with different stock.

### 1.4 — cart and shipping tables
`carts`, `cart_items` and `shipping_methods` are in migration 0003. The one-active-cart-per-user rule is a partial unique index on `user_id WHERE status = 'active'`, so the database refuses a second live cart even if two requests race, while merged/converted/abandoned history and any number of guest carts (NULL user ids never collide) stay allowed. Cart items carry no price, only a variant and a quantity (checked 1 to 99, unique per cart), because the cart is re-priced from the catalog on every read. The test inserts a second active cart and expects a rejection, then shows a new one is allowed once the old one is converted.

### 1.5 — order, payment, webhook and history tables
Migration 0004 adds `orders`, `order_items`, `payments`, `webhook_events` and `order_status_history`, the `order_number_seq` sequence (the order number is a column default built from it) and the check constraints. The test proves a wrong total, a wrong line total and a duplicate webhook event id are all rejected, and that order numbers are unique and well-formed. Order items copy the product name, variant name, SKU, image and unit price instead of pointing at the live variant, because the catalog changes (renames, price changes, deletions) while an order is a legal record of what was agreed at that moment. A check constraint is the last line of defence: application code can have bugs or be bypassed by a script, but the database refuses an inconsistent row no matter who writes it.

### 1.6 — seed data
`src/db/seed/` holds the categories (5 pets, 20 sub-categories with per-pet accent colour and icon), 40 hand-written products, the two shipping methods and three demo users with argon2id hashes; `expand.ts` turns each product's option axes into variants with SKUs, prices, weights, image rows and deterministic stock (211 variants, 63 images, a few sold out and a few low). Every table is written with `INSERT ... ON CONFLICT DO UPDATE` keyed on slug, SKU, code or email (inventory is insert-only so a re-seed never resets stock), and a test proves two runs give identical counts. `pnpm db:reset` drops both schemas, migrates and seeds, and refuses to run in production or against a non-local host. `ON CONFLICT DO UPDATE` makes an insert into "insert, or update the row that already has this unique key", which is why the seed is idempotent; seeds are code rather than SQL dumps because code can derive 211 variants from 40 products, is type-checked against the schema, and cannot silently rot when a column changes. Images are AI-generated by a separate step rather than downloaded, so the rows and paths exist now and the files arrive later through `pnpm images:process` (sharp cover-crops to 1200 and 600 pixel WebP); the licence question becomes "which tool and prompt made this", recorded in `CREDITS.md`.

### 1.7 — test database harness
A vitest `globalSetup` migrates the test database once per run, and a `setupFiles` hook truncates every public table (list read from `pg_tables`) before each test and closes the pool after each file; both refuse to run unless the database name ends in `_test`. `fileParallelism: false` keeps files from sharing the database at the same time, and three factories (`createUser`, `createProduct({variants})`, `createCart`) build valid rows with unique slugs, SKUs and emails. A new test proves a row written in one test is gone in the next, and the earlier table tests were simplified to use the harness instead of cleaning up after themselves. Truncating per test is simple and, with these tiny tables, fast enough; the alternative (wrapping each test in a rolled-back transaction) is faster but breaks code that opens its own transactions, which checkout will.

## Phase 2 — API foundation

### 2.1 — request id and logging
Every request now gets an id: the caller's `X-Request-Id` if it looks like a safe id, otherwise a fresh UUID. It is set on `req.id`, echoed in the response header and used by `pino-http` as the log line's request id. The logger redacts the cookie, authorization and set-cookie headers, prints pretty output only in development and JSON otherwise. Tests capture the log stream to prove the id is on the access log and that secrets never appear. Learn: structured logs are one JSON object per line, so a log tool can filter on fields instead of parsing sentences; redaction exists because logs outlive and spread wider than the database; one id passed web, api and Stripe lets you follow a single checkout through all three systems' logs.

### 2.2 — domain errors and error middleware
`AppError(code, message, details)` is the only error services throw; its status comes from the shared code-to-status table, and small factories (`notFound`, `validation`, `conflict(code)` ...) keep call sites short. The error middleware is the one place errors become HTTP: `AppError` gives its own status, a `ZodError` becomes 400 with flattened issues, parser errors (bad JSON, too large) become 400/413, and everything else is logged with its stack and answered with a generic 500 in production. An unknown route falls through to a JSON 404. The shared package had to learn to be imported by the API (workspace dependency, `.ts` extensions in its relative imports, `allowImportingTsExtensions` in the base tsconfig) because the API compiles it under NodeNext. Learn: throwing a typed error keeps rules out of the HTTP layer, and never leaking a stack trace matters because a stack names files, libraries and queries an attacker can use.

### 2.3 — Zod validation middleware
`validate({ body, query, params })` parses each part with its Zod schema and stores the results on `req.valid`; a failure throws a `ZodError`, which step 2.2's middleware turns into a 400. Handlers read the values with `valid(req, schemas)`, which gives them their inferred types (coerced numbers, defaults applied). `respond(res, schema, data, meta?)` sends the `{ data, meta }` envelope and, outside production, first checks the data against the endpoint's schema, failing with a 500 if our own output drifts from the contract. Express 5 made `req.query` read-only, which is why parsed values go on `req.valid`. Learn: validating at the edge means everything inside the app can trust its types; validating output catches the bug in our tests instead of in the web client.

### 2.4 — security middleware
The app now runs `helmet`, CORS limited to `WEB_ORIGIN` with credentials, a global rate limit (429 in the normal error envelope, health exempt), signed `cookie-parser`, a 100 kB JSON limit and a CSRF origin check on every non-GET request except the Stripe webhook prefix. `trust proxy` is 1 only in production. A stricter limiter factory for login is ready for phase 6 and keys on IP plus email. Config is validated in `env.ts` (a production boot without `COOKIE_SECRET` fails) and passed into `createApp` as one `config` object. Learn: helmet sets headers such as `Strict-Transport-Security` (stay on HTTPS), `X-Content-Type-Options: nosniff` (no MIME guessing), `X-Frame-Options` (no clickjacking frames), a restrictive `Content-Security-Policy` and `Referrer-Policy`. Origin checking is enough with `SameSite=Lax` because the cookie is not sent on cross-site POSTs and a page cannot forge its `Origin`, so two independent layers must both fail. Rate limits are keyed by IP so one noisy client cannot starve others, and by email on login so one attacker cannot lock out a victim from everywhere.

### 2.5 — database health check and graceful shutdown
`GET /api/v1/health` now runs `select 1` raced against a 1 s timer and returns `{ status, db, version }` with 200, or 503 (`degraded`/`down`) plus a logged error carrying the request id. The version is read from `package.json` at startup. `index.ts` now keeps the server handle and, on SIGTERM/SIGINT, stops accepting connections, closes idle sockets, closes the DB pool and exits 0; if anything has not finished after 10 s it exits 1. The logic lives in `lib/shutdown.ts` with the exit function injected so tests can check it, and I also sent a real SIGTERM to the running server and saw "shutdown complete". Learn: platforms stop a service by sending SIGTERM and killing it after a grace period, so finishing in-flight requests and releasing connections prevents dropped checkouts and leaked database connections on every deploy.

### 2.6 — module layout and router mounting
`src/modules/index.ts` mounts the `catalog`, `auth`, `cart`, `checkout` and `admin` routers at the root of `/api/v1`; each folder has a `router.ts` exporting an empty router so later phases only add files. Routers declare their full sub-paths (`/products`, `/auth/login`), so a path from the API contract can be found by searching the code. `.env.example` was already updated in 2.4. A final test checks the phase's acceptance criterion: a bad JSON body, an unknown route, a foreign-origin POST and a database outage each give the right status and a log line carrying the request id. Router variables carry an explicit `Router` type annotation because TypeScript otherwise refuses to name the pnpm-internal type.

## Phase 3 — Catalog API

### 3.1 — shared catalog schemas
`packages/shared/src/schemas/` now has `common.ts` (the `{ data }` / `{ data, meta }` envelopes, pagination meta and query) and `catalog.ts` (category, product card, variant, product detail, facets and the list query). The list query schema moves every `attr.<key>` parameter into an `attr` record, splits comma lists into arrays, coerces numbers, turns `inStock=true|false` into a boolean, caps `limit` at 100, rejects `minPrice > maxPrice` and strips unknown parameters. `respond()` from step 2.3 now takes the whole envelope schema so the web can parse responses with the same schema the API validated against. Learn: sharing one schema file means a change to a response shape is a type error in both the API and the web at once, instead of a bug found in the browser.

### 3.2 — category endpoints
`GET /api/v1/categories` returns the whole tree and `GET /api/v1/categories/:slug` one category with its children, both validated against the shared schemas. The repo does one query with a grouped count of active products joined in (not one count per category), the service builds the tree and rolls children's counts up into their parent, and the router only validates and responds. A missing slug is a `notFound()` thrown by the service, because the repo never throws domain errors. The factories gained `createCategory` and options on `createProduct` (category, attributes, images, stock details) that the later steps use. Learn: one grouped join keeps the endpoint at constant query count however many categories exist.

### 3.3 — product list: base query, pagination, sort
`GET /api/v1/products` returns active products as cards: a join to a per-product summary of active variants (min and max price, currency, any stock left), the category slug, and one primary image fetched for the page's products in a second query (`DISTINCT ON`, product-level images first). A separate count query gives `meta.total`. Sorting has a map for `price_asc`, `price_desc`, `newest` and `name`, every one ending in `products.id` so ties cannot reorder between pages; `relevance` without a search term falls back to newest. Learn: offset pagination (`LIMIT/OFFSET`) is simple and lets the shopper jump to page N; keyset pagination is faster for deep pages and infinite feeds but cannot jump and needs a stable sort key, and with 40 products (and at most a few thousand ever) the offset cost is invisible, so simple wins. `EXPLAIN ANALYZE` on the dev seed (40 products, 211 variants): sequential scans on the three small tables, a hash aggregate for the variant summary, a hash join, an index scan on `categories_pkey`, top-N sort, 0.56 ms; at this size Postgres rightly ignores indexes, and the GIN and foreign key indexes matter once the tables grow.

### 3.4 — product filters
The list accepts `category` (the category plus its children), `minPrice`/`maxPrice` (a product matches if any active variant is in range), `inStock`, and `attr.<key>=v1,v2`. Each filter is a Drizzle `sql` fragment returned by one `filterConditions()` function and combined with `and()`, and the list and count queries both use it so `meta.total` always matches. Attribute filters use jsonb containment (`attributes @> {"material":"plush"}`), OR-ed within a key and AND-ed across keys, with values bound as parameters. Tests cover each filter, an injection attempt and a combination with sort and paging. Learn: `@>` can use the GIN index on `attributes`, while `attributes->>'material' = 'plush'` cannot, and binding values as parameters is what stops SQL injection.

### 3.5 — full-text search
`q` is compiled with `websearch_to_tsquery('english', q)` and matched against the generated `search_vector` with `@@`; `sort=relevance` (the default when `q` is present) orders by `ts_rank`, then newest, then id. One or two characters, and queries made only of stop words, fall back to a case-insensitive substring match on the name, with `%` and `_` escaped. Tests show "rope" finding both rope toys, "parrot" finding a bird product through its description, stemming, quoted phrases and exclusion, and that a real typo finds nothing: typo tolerance is not promised, and the contract now says so. Learn: a `tsvector` is the text reduced to stemmed, de-stop-worded lexemes with positions; a `tsquery` is the same for the search, and `@@` asks whether the vector satisfies the query; `plainto_tsquery` ANDs all words and has no syntax, `websearch_to_tsquery` adds quotes, `or` and `-` and never raises a syntax error on user input, so it is the safe choice for a search box; `ts_rank` scores by how often and how densely the words appear.

### 3.6 — facets
The list response now carries `facets: { attributes, price }` next to `data` and `meta`. Attribute counts come from one grouped query that expands each product's jsonb with `jsonb_each_text`, restricted to the `FACET_KEYS` (`pet`, `material`, `brand`, `ageStage`); the price range is the min and max over the same products. The facets are computed over the browsing scope (category with children, plus the search term) and deliberately ignore the attribute, price and stock filters, so the other values keep their counts and the shopper can switch between them. Every key is always present, empty if nothing matches. The filter code was split into `scopeConditions` (shared by list, count and facets) and `filterConditions` (scope plus narrowing filters). Learn: grouping by key and value in a single pass is what makes the filter UI data-driven without a query per filter.

### 3.7 — product detail
`GET /api/v1/products/:slug` returns the product with its active variants (cheapest first, with `compareAtPriceCents`, `isDefault`, `available` and `lowStock`), images in sort order (variant-specific ones carry their `variantId`), the public attributes, `optionKeys` split out of the attributes jsonb, a root-first breadcrumb (parent category then category) and the price range and `inStock`. Availability is `quantity - reserved > 0` and low stock is available units at or below the variant's threshold; the raw numbers never leave the service, and a test checks the JSON for any stock field names. Draft, archived, unknown and no-active-variant products are all the same 404. Learn: exposing booleans instead of counts avoids leaking sales velocity, and keeping the rule in the service means the router and the repo stay free of business logic.

### 3.8 — caching headers
Catalog GETs (`/categories`, `/categories/:slug`, `/products`, `/products/:slug`) now send `Cache-Control: public, max-age=60, stale-while-revalidate=300`; Express's default weak `ETag` is already on every JSON response and a conditional request gets a 304. The header is applied by a middleware scoped to those paths (the catalog router is mounted at the API root, so an unscoped one would have leaked onto cart and account), and the error handler overwrites it with `no-store`, so a 404 or 400 is never cached as data. The contract documents that an admin change can lag up to 60 s publicly. Learn: `max-age` lets browsers and the CDN reuse a response without asking; `stale-while-revalidate` lets them serve a slightly old copy instantly while fetching a fresh one in the background; the ETag lets a client that does ask pay only for a 304 instead of the whole body.

## Phase 4 — Web foundation

### 4.1 — Tailwind and design tokens
Colours live as plain CSS variables in `src/styles/tokens.css`; `tailwind.config.ts` only gives them utility names (`bg-primary`, `text-pet-strong`), so putting `data-pet="cat"` on any wrapper re-themes every `pet-*` utility beneath it without JavaScript. Each pet defines three roles: a bright `accent` for fills (text on it is always ink), a pastel `soft` for backgrounds that sits well next to the pastel product photos, and a dark `strong` shade for text. A vitest file parses `tokens.css` itself and asserts WCAG AA (4.5:1) for every text pairing the UI uses, so a colour edit that breaks contrast fails the build. Fonts are Fredoka (rounded display) and Nunito Sans (body) from `@fontsource-variable`, bundled by Vite: no request to Google at runtime, one file per font covers every weight. The trade-off of utility CSS is long class lists in exchange for no naming, no dead CSS and a design system enforced by the config; the base layer (`globals.css`) holds the focus ring and the reduced-motion rule.

### 4.2 — UI primitives
`components/ui/` has Button, Input, Select, Checkbox, Badge, Skeleton, Dialog, Toast, Price, Spinner and VisuallyHidden, each with a test of its accessibility contract (role, accessible name, keyboard, described-by). Form controls require a `label` prop, so an unlabelled field cannot be written; the accessible name is what a screen reader speaks and what Testing Library's `getByRole(..., { name })` queries, which is why the tests double as an accessibility check. Dialog is a native `<dialog>` opened with `showModal()`, so the browser supplies the focus trap (everything behind is inert), Escape and focus return. Toast keeps two live regions (polite for info/success, `role="alert"` for errors) mounted before any message exists, because screen readers only announce changes inside a region that was already there; error toasts never auto-dismiss.

### 4.3 — layout
`components/layout/` holds Container (the single source of page width and gutters), SkipLink, Header, AccountMenu, SearchBox, MobileNav, Breadcrumbs, Footer and `AppLayout`, the frame that renders every route through `<Outlet />`. Landmarks are `header`, two labelled `nav`s, `main` and `footer`, and the skip link is the first tab stop; on phones the search wraps to its own full-width row so the top row (menu, logo, account, cart) fits at 360 px. The pet navigation reads a typed constant in `lib/pets.ts` (slug, name, `data-pet` accent, icon) so the shell needs no request; phase 5 can replace it with category data from the API if we want admin-editable categories. The cart badge count is a prop, not a fetch, because the cart feature (phase 7) will own that number. Landmarks matter because screen-reader users jump between them instead of reading linearly.

### 4.4 — routing
`routes.tsx` is one table of every route, wrapped in `AppLayout`; checkout, confirmation, account and admin use route-level `lazy()` and the build confirms each becomes its own small chunk, while the storefront pages stay in the main bundle. The data router (`createBrowserRouter`) is used instead of `<Routes>` because only it supports `lazy`, `errorElement` and later loaders. A pathless child route carries the `errorElement`, so when a page throws, the header and footer stay and only the main area shows "Something went wrong" (React would otherwise unmount the whole app to a blank page); the layout has its own bare fallback if it is the thing that breaks. `ScrollRestoration` lives in the layout. The router is created in `main.tsx`, not at import time, because creating a browser router reads `window`. Pages are minimal placeholders that say which phase builds them; `NotFoundPage` and `RouteErrorPage` are already real, so 4.7 only needs the Loading polish and Home.

## Product images (between phases 3 and 5)
The 63 product photos were generated with Gemini in the browser, one fresh chat per product so the close-up (`-2`) shows the same item as the main shot. A shared style line (pastel background in the pet's accent colour, no text, no animals) keeps the set consistent. `pnpm images:process` cover-crops each to a 1200px and a 600px WebP; the 600px one feeds `srcset` on product cards so phones download a quarter of the pixels. ## Phase 6 (API) — Auth and accounts

### 6.1 — password hashing + session store
`password.ts` wraps argon2id (64 MiB, 3 passes, 1 lane) and also owns a lazily computed dummy hash that login will verify against when an email is unknown, so both failures cost the same time. `sessions.ts` mints a 32-byte random token, stores only its SHA-256 in `sessions.id`, and `getSession` joins the user with explicit columns (the password hash can never leak upward), rejects expired rows in the query, and slides the expiry at most once an hour. `deleteOtherSessions` and `purgeExpired` cover password-change revocation and cron-less cleanup.
Learn: argon2id beats bcrypt because its memory cost makes GPU cracking expensive and bcrypt is capped at 72 bytes; a session fixation attack plants a known session id before login, so login must always issue a fresh one; sliding expiry keeps active users signed in without a write on every request.

### 6.2 — cookie + auth middleware
`lib/cookies.ts` is the only place the `sid` cookie's attributes are decided (HttpOnly, SameSite=Lax, Secure in production, path `/`, 30 days, no Domain), and the clear call reuses them because a browser ignores a clear whose attributes differ. `attachUser` loads the user from the cookie on the personal routes only and never rejects: no or bad cookie means `req.user = null`, while a down database still surfaces as a 500. `requireUser` answers 401, `requireAdmin` answers 401 for anonymous and 403 for customers.
Learn: HttpOnly hides the cookie from XSS, SameSite=Lax withholds it from cross-site POSTs, Secure keeps it off plain HTTP; the middleware is tested on a tiny standalone app before any real route depends on it.

### 6.3 — register / login / logout / me
Shared `RegisterSchema`, `LoginSchema`, `UserSchema` (strict, so a stray hash fails in dev/test) and `UserResponseSchema` are the single contract for API and web. Register inserts with `ON CONFLICT DO NOTHING` (409 when nothing came back); login verifies against the real hash or a dummy one so an unknown email costs the same as a wrong password, answers with one generic message, and always destroys the session cookie that arrived before issuing a new id. The credential limiter (10 per 15 min, keyed by IP + normalised email) sits before validation, and `onLogin` is an empty hook where phase 7.4 plugs in the cart merge.
Learn: NIST asks for length and a block-list instead of composition rules; registration may reveal that an email exists but login must not; the fixation fix is "never reuse a session id across a privilege change".

### 6.4 — account and address endpoints
`/account` (names), `/account/password`, address CRUD and the empty-for-now order list live in `modules/account`, all behind `requireUser` and all scoped by `req.user.id`, never by an id from the request. The password change verifies the current password, rehashes, and deletes every other session; a wrong current password is a field error (400) so the web does not mistake it for an expired session. Address writes run in a transaction that first locks the user row, demotes the previous default and then writes (the partial unique index would reject the other order), and a foreign id fails inside the transaction so even the demotion rolls back.
Learn: IDOR means trusting an id from the URL, fixed by putting the owner in the WHERE clause and answering 404 for both "missing" and "not yours"; `SELECT ... FOR UPDATE` turns a race into a queue; revoking other sessions is what makes a password change actually evict an attacker.

## Phase 7 (API) — Cart

### 7.1 — cart identity
`withCart` decides which cart a request works on: the signed-in user's single active cart, or the guest cart named by the signed `cart_id` cookie, creating either lazily on first use. The cookie only counts if its HMAC verifies and the row is still an active, ownerless, unexpired cart; for a user the cookie is ignored. The cart id therefore always comes from the server, never from a body or URL, which is the whole IDOR defence for the mutation steps. Races on a user's first cart are absorbed by `ON CONFLICT DO NOTHING` plus a re-read.
Learn: signed cookies stop tampering but are readable, encrypted cookies hide the value too (not needed for a uuid); the cart is a server resource keyed by identity, so the client never sends a cart id; lazy creation avoids one empty row per bot.
